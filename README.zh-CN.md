# 热量记录（Calorie Tracker）

[English](README.md) | **简体中文**

一个放在手机主屏幕上用的热量和三大营养素记录工具。离线优先，不联网也能用。它用 AI 识别食物，模型读出的每个数都要过一遍算术交叉验证，也就是用简单的算术把几个数互相核对。能量平衡（吃进和消耗的热量之差）用到的常数，每周用真实的晨重（早上起床后称的体重）数据重新校准。

**在线使用：** https://jackyyangjq.github.io/caltrk/ （可以添加到 iOS 主屏幕；所有数据都留在浏览器里）。界面是中文的。

## 功能

- **一键记录。** “快速记录”里的食物按时间加权的使用频率排序：最近 7 天用过一次，大约抵得上一个月前用过三次。每个食物有两个可点的位置：一个按常用份量记（一勺、一个、一包），一个按“上次 N g”记，也就是上次称的克数。每条记录记下后的几秒内都能撤销。
- **AI 识别，自带密钥。** 用的是你自己申请的模型服务密钥。可以拍一餐、拍营养成分表，或者打字描述。视觉模型（能看懂图片的 AI 模型）返回一个 JSON 对象，也就是一份结构化数据，内容是每 100 g 的热量、蛋白质、脂肪、碳水，以及整包重量和建议份量。你在确认面板里核对好名称和克数之前，什么都不会保存。
- **模型读的每张标签都要交叉验证。** 第一项是 Atwater 校验，用的是营养学通用的换算：蛋白质、碳水、脂肪每克分别算 4、4、9 千卡。据此算出的热量和标签上印的热量相比，偏差超过 30% 就标出来。第二项是整包校验：用每 100 g 的热量乘以整包克数，和标签上印的整包热量相比，偏差超过 12% 就标出来。这一项能抓住一种常见错误：把“每份”那一栏当成“每 100 g”来读。还可以让第二个模型把同样的照片再读一遍，应用会比对两次读数的差别。
- **每日额度和营养素。** 剩余热量、蛋白质目标、碳水和脂肪上限、训练记录、晨重锚点（体重以早上起床后称的为准）、近 7 天和 14 天的历史。还能打开过去任何一天，补记或修改。
- **体重趋势。** 晨重画成散点，上面是一条指数平滑的趋势线（Hacker's Diet 的做法，α = 0.1，没称的日子按前后插值）；下面另一块按同一日期轴画每天摄入（没打「记全了」的画成空心），带目标和基准消耗两条参考线。可切 2 周 / 1 个月 / 全部，点按或用方向键看任意一天的数，也有表格。按趋势线算近 7 天、近 14 天每周掉多少，和计划的 0.4–0.5 kg/周对比。
- **什么都不离开手机。** 唯一的例外，是你主动发给模型接口的照片或文字。数据存在 localStorage（浏览器自带的本地存储）里；导出是一个 JSON 文件；存储损坏会被检测出来，原始数据会被抢救进导出文件。

## AI 识别是怎么工作的

```
照片 / 文字
  ──▶ 兼容 OpenAI 格式的 chat-completions 接口（模型可在应用里选）
      系统提示词（给模型的固定指令）：“只输出一个 JSON 对象” ──▶ 解析
  ──▶ 算术交叉验证（Atwater、整包） ──▶ 可选：第二个模型比对
  ──▶ 确认面板（改名称 / 克数） ──▶ 记入饮食记录
```

模型从不直接写入饮食记录。请求失败或超时（60 秒）时，应用会引导你改用手动的“记一条估计”，这一餐照样能记下来。

## 常数怎么校准

基准消耗（平均每天消耗的总热量）和每日目标（每天计划吃多少热量）这两个常数，不是估一次就放着不管。每周复盘时，先用最小二乘法（最常用的趋势线拟合方法）给晨重拟合出趋势，再反推能量平衡，也就是倒算每天实际消耗了多少热量。然后把结果和稳健拟合（不容易被个别异常读数带偏）、分段拟合（把时间切成几段分别拟合）对照。只有当区间（估计值的可信范围）窄到能说明问题时，常数才会调整。

- 第 1 次复盘（5 个晨重数据）：正确地得出“数据不够”的结论，常数不变。
- 第 3 次复盘（18 天里的 16 个晨重数据）：第一次出现统计显著的趋势，即不太可能只是随机波动；两个常数都更新了。

常数写在发布的程序里，不存在 localStorage 里。所以发布新版本就能更新常数，不会碰到用户的记录。

## 设计取舍

- **不用框架，原生 ES 模块，用 Vite 打包。** 1.17 及以前是单个 HTML 文件、没有构建步骤（到最后约 3,100 行）。2.0 在行为完全不变的前提下拆成了 `src/` 下的模块：纯计算逻辑在 `src/lib/`（有单元测试），周报要改的数据在 `src/build.js` 和 `src/data/`，每个页面一个模块在 `src/views/`。源码不打包也能直接用静态服务器打开；GitHub Actions 负责测试、构建、发布到 Pages。
- **离线优先，只用 localStorage。** 没有账号，没有服务器。最早的三次提交都是存储探针，也就是专门做验证的小实验版本。要验证的是：GitHub Pages 重新发布后，数据还在不在；iOS 上从主屏幕打开的应用有单独的存储容器，数据在那里能不能留住。
- **精选内置食物库，修正用覆盖层。** 内置食物大多是英国超市的商品，数值都从标签上读取，并且通过了算术交叉验证。用户自己添加的食物，要用过至少两次、并通过验证，才会转正，进入内置食物库。修正和合并在读取时以覆盖层的方式叠加：显示时盖上一层改动，底下的原数据不动。所以已经存在手机里的条目永远不会被改写。
- **模型调用不绑定某一家服务商。** 只有一个请求函数，对接兼容 OpenAI 格式的 chat-completions 接口（很多模型服务都支持这种格式），默认经过一个代理转发。模型可以从下拉列表里选，也可以手动填写。不同模型系列的参数差异都集中在一处处理，比如有的模型不接受自定义 temperature（控制输出随机程度的参数）。

## 开发

```
npm install
npm run dev        # 本地开发服务器，改了自动刷新
npm run lint       # 抓未定义的名字、漏掉的 import
npm test           # 单元测试（纯函数、食物库数据完整性、BUILD 常数）
npm run test:e2e   # 先构建，再用无头 Chromium 把每个页面和流程走一遍（AI 和 Open Food Facts 用假数据）
node tests/e2e/compare.mjs <旧版目录> dist   # 新旧两版逐步对比：页面、本地存储、导出文件
```

周报要改的：`src/build.js`（校准常数）、`src/data/foods.js` 和 `src/data/logfix.js`（食物库、覆盖层、流水更正）。`npm test` 会检查份量、营养素上限、更正条目是否还自洽。推送到 `main` 就自动发布（仓库设置 → Pages → Source 需选「GitHub Actions」）。

## 如果重来，我会怎么改

- 文件超过大约 1,500 行时就该拆成模块。为此加一个构建步骤，完全划得来。（2.0 已做，晚了些。）
- 给纯函数（输出只取决于输入的函数）配一套小测试：Atwater 校验、按时间加权的排序、每天的起止边界。（2.0 已做。）
- 把校准用的拟合搬进应用里，让每周复盘自动闭环，算出的结果直接用上。
