# 热量记录（Calorie Tracker）

[English](README.md) | **简体中文**

一个放在手机主屏幕上用的热量和三大营养素记录工具。离线优先，不联网也能用。它用 AI 识别食物，模型读出的每个数都要过一遍算术交叉验证，也就是用简单的算术把几个数互相核对。能量平衡（吃进和消耗的热量之差）用到的常数，每周用真实的晨重（早上起床后称的体重）数据重新校准。

**在线使用：** https://jackyyangjq.github.io/caltrk/ （可以添加到 iOS 主屏幕；所有数据都留在浏览器里）。界面是中文的。

## 功能

- **一键记录。** “快速记录”里的食物按时间加权的使用频率排序：最近 7 天用过一次，大约抵得上一个月前用过三次。每个食物有两个可点的位置：一个按常用份量记（一勺、一个、一包），一个按“上次 N g”记，也就是上次称的克数。每条记录记下后的几秒内都能撤销。
- **用 Claude 做 AI 识别，自带密钥。** 你自己的 Anthropic API 密钥贴一次就行，页面从手机直接调用 Claude API。可以拍一餐、拍营养成分表，或者打字描述。Claude Sonnet 5.5 返回一个 JSON 对象，也就是一份结构化数据，内容是每 100 g 的热量、蛋白质、脂肪、碳水，以及整包重量和建议份量。你在确认面板里核对好名称和克数之前，什么都不会保存。
- **份量档位、语音、通用食物库。** 拍一餐、文字或语音估算时，每样东西附 2–4 个份量档位（小碗/中碗/大碗、半盘/一盘），点一下就换克数，不用自己输。🎤 按钮最长听 30 秒，用浏览器自带的语音识别（Web Speech API，中文）边说边转成文字，再按文字估算发给 Claude（Claude API 不收音频），确认面板顶部显示「听到的是」。搜索时还会列出通用食物库：513 种常见食物（米饭、鸡肉、蔬菜水果、豆腐、常见外卖菜……），数值来自 USDA SR Legacy，配了中文名、别名和常用份量。
- **模型读的每张标签都要交叉验证。** 第一项是 Atwater 校验，用的是营养学通用的换算：蛋白质、碳水、脂肪每克分别算 4、4、9 千卡。据此算出的热量和标签上印的热量相比，偏差超过 30% 就标出来。第二项是整包校验：用每 100 g 的热量乘以整包克数，和标签上印的整包热量相比，偏差超过 12% 就标出来。这一项能抓住一种常见错误：把“每份”那一栏当成“每 100 g”来读。标签没读全时，先按条形码查 Open Food Facts，查不到再让 Claude 联网搜索同款商品的官方营养表，把缺的数补上。还可以让 Claude Opus 5.5 把同样的照片再读一遍，应用会比对两次读数的差别。
- **每日额度和营养素。** 剩余热量、蛋白质目标、碳水和脂肪上限、训练记录、晨重锚点（体重以早上起床后称的为准）、近 7 天和 14 天的历史。还能打开过去任何一天，补记或修改。
- **体重趋势。** 晨重画成散点，上面是一条指数平滑的趋势线（Hacker's Diet 的做法，α = 0.1，没称的日子按前后插值）；下面另一块按同一日期轴画每天摄入（没打「记全了」的画成空心），带目标和基准消耗两条参考线。可切 2 周 / 1 个月 / 全部，点按或用方向键看任意一天的数，也有表格。按趋势线算近 7 天、近 14 天每周掉多少，和计划的 0.4–0.5 kg/周对比。
- **什么都不离开手机。** 例外只有两个：你主动发给 Claude API 的照片或文字；用 🎤 时的语音——它由浏览器自带的语音识别转成文字（iPhone 能在本机识别时在本机，否则交给苹果的服务器；Chrome 交给谷歌），只有转出的文字发给 Claude。数据存在 localStorage（浏览器自带的本地存储）里；导出是一个 JSON 文件；存储损坏会被检测出来，原始数据会被抢救进导出文件。

## AI 识别是怎么工作的

```
照片 / 文字 / 语音转的文字
  ──▶ Claude Messages API（claude-sonnet-5-5，官方 JS SDK，从浏览器直连）
      结构化输出：回复必须符合给定的 JSON 结构 ──▶ 范围检查 ──▶ 解析
  ──▶ 算术交叉验证（Atwater、整包）
  ──▶ 标签没读全？按条形码查 Open Food Facts，查不到再用 Claude 联网搜索
  ──▶ 可选：Claude Opus 5.5 再读一遍标签，比对两次读数
  ──▶ 确认面板（改名称 / 克数） ──▶ 记入饮食记录
```

模型从不直接写入饮食记录。请求失败或超时（每次 60 秒，自动重试一次）时，应用会引导你改用手动的“记一条估计”，这一餐照样能记下来。

## 常数怎么校准

基准消耗（平均每天消耗的总热量）和每日目标（每天计划吃多少热量）这两个常数，不是估一次就放着不管。每周复盘时，先用最小二乘法（最常用的趋势线拟合方法）给晨重拟合出趋势，再反推能量平衡，也就是倒算每天实际消耗了多少热量。然后把结果和稳健拟合（不容易被个别异常读数带偏）、分段拟合（把时间切成几段分别拟合）对照。只有当区间（估计值的可信范围）窄到能说明问题时，常数才会调整。

- 第 1 次复盘（5 个晨重数据）：正确地得出“数据不够”的结论，常数不变。
- 第 3 次复盘（18 天里的 16 个晨重数据）：第一次出现统计显著的趋势，即不太可能只是随机波动；两个常数都更新了。

常数写在发布的程序里，不存在 localStorage 里。所以发布新版本就能更新常数，不会碰到用户的记录。

## 设计取舍

- **不用框架，原生 ES 模块，用 Vite 打包。** 1.17 及以前是单个 HTML 文件、没有构建步骤（到最后约 3,100 行）。2.0 在行为完全不变的前提下拆成了 `src/` 下的模块：纯计算逻辑在 `src/lib/`（有单元测试），周报要改的数据在 `src/build.js` 和 `src/data/`，每个页面一个模块在 `src/views/`。2.3 起用了 Anthropic 官方 SDK（运行时依赖），源码要经 Vite 打开（`npm run dev`），不能再直接用静态服务器打开；GitHub Actions 负责测试、构建、发布到 Pages。
- **离线优先，只用 localStorage。** 没有账号，没有服务器。最早的三次提交都是存储探针，也就是专门做验证的小实验版本。要验证的是：GitHub Pages 重新发布后，数据还在不在；iOS 上从主屏幕打开的应用有单独的存储容器，数据在那里能不能留住。
- **精选内置食物库，修正用覆盖层。** 内置食物大多是英国超市的商品，数值都从标签上读取，并且通过了算术交叉验证。用户自己添加的食物，要用过至少两次、并通过验证，才会转正，进入内置食物库。修正和合并在读取时以覆盖层的方式叠加：显示时盖上一层改动，底下的原数据不动。所以已经存在手机里的条目永远不会被改写。
- **用官方 SDK 调 Claude API，不加后端。** 2.2 及以前接的是兼容 OpenAI 格式的中转、模型可选；2.3 整体换成 Claude API。密钥是用户自己的、只存在他自己的浏览器里，所以 SDK 直接在网页里跑（开 `dangerouslyAllowBrowser`），中间没有服务器。SDK 单独打成一个文件，第一次用 AI 时才加载：平时打开应用不用多下载、多解析它，万一某个浏览器加载不了，也只影响 AI 功能。回复用结构化输出约束（每类请求一个 JSON 结构），不再靠提示词求模型“只输出 JSON”；原来的范围检查和算术交叉验证照样在后面跑。思考深度按任务设：拍照用 `medium`，文字和联网搜索用 `low`。联网搜索用 Claude 的服务端工具，是唯一不带结构约束的请求，因为搜索结果带引用，而结构化输出不能和引用一起用。

## 数据来源

- **通用食物库**（`data/generic-foods.json`）：营养数值来自 [USDA FoodData Central 的 SR Legacy](https://fdc.nal.usda.gov/)（公有领域）。因为构建环境连不上 USDA 网站，数值取自 [tempo-food-db](https://www.npmjs.com/package/tempo-food-db) 整理版（TempoLife，CC-BY-4.0）。中文名、别名、份量是逐条整理的；营养数按英文原名从数据集里精确匹配，一个数都没有手填。碳水按英国标签口径扣除了膳食纤维。
- **条形码**：[Open Food Facts](https://world.openfoodfacts.org/)（ODbL），实时查询，不转存。

## 开发

```
npm install
npm run dev        # 本地开发服务器，改了自动刷新
npm run lint       # 抓未定义的名字、漏掉的 import
npm run build:foods  # 用 scripts/generic-foods/*.json + USDA 数值重新生成 data/generic-foods.json
npm test           # 单元测试（纯函数、食物库数据完整性、BUILD 常数）
npm run test:e2e   # 先构建，再用无头 Chromium 把每个页面和流程走一遍（AI 和 Open Food Facts 用假数据）
node tests/e2e/compare.mjs <旧版目录> dist   # 新旧两版逐步对比：页面、本地存储、导出文件
```

周报要改的：`src/build.js`（校准常数）、`src/data/foods.js` 和 `src/data/logfix.js`（食物库、覆盖层、流水更正）。`npm test` 会检查份量、营养素上限、更正条目是否还自洽。推送到 `main` 就自动发布（仓库设置 → Pages → Source 需选「GitHub Actions」）。

## 如果重来，我会怎么改

- 文件超过大约 1,500 行时就该拆成模块。为此加一个构建步骤，完全划得来。（2.0 已做，晚了些。）
- 给纯函数（输出只取决于输入的函数）配一套小测试：Atwater 校验、按时间加权的排序、每天的起止边界。（2.0 已做。）
- 把校准用的拟合搬进应用里，让每周复盘自动闭环，算出的结果直接用上。
